## План работы

### Этап 1. Измерения и CLI

Создать `download_speed.py`. Принимать обязательный HTTP/HTTPS URL, `--timeout SECONDS`, `--version` и стандартные `-h`/`--help`. Проверять наличие хоста и конечный положительный таймаут; NaN и бесконечность недопустимы. Десять загрузок выполнять строго последовательно. Читать тело блоками по 64 KiB без сохранения на диск. Считать реально прочитанные байты, независимо от наличия `Content-Length`.

Использовать GET с `Accept-Encoding: identity`, чтобы запросить несжатое представление. Если сервер всё же прислал сжатое тело, считать полученные байты без автоматической распаковки. Сохранять стандартную проверку TLS и обычную поддержку HTTP/HTTPS-перенаправлений urllib. При известном `Content-Length` обнаруживать преждевременный конец тела и считать его ошибкой. Не требовать этот заголовок от сервера.

При HTTP-ошибке, проблеме соединения, таймауте или оборванном ответе остановить выполнение: сообщение в stderr, код 1, без итоговой успешной скорости и без повторов. Неверные аргументы дают код 2 средствами argparse. Ctrl+C (SIGINT) завершает работу без traceback с кодом 130. SIGTERM обрабатывается через стандартный модуль `signal`: короткое сообщение в stderr, завершение с кодом 143, без traceback и без итоговой скорости. Коды соответствуют соглашению 128 + номер сигнала. Обработчик устанавливать в `main` на время выполнения CLI, а предыдущий обработчик восстанавливать в `finally`; импорт модуля и вызов `measure` не должны менять обработчики процесса. Для прерывания текущего чтения обработчик поднимает отдельное исключение завершения, которое перехватывается на уровне CLI; открытый ответ закрывается контекстным менеджером. Такой механизм не обещает мгновенного прерывания любой системной операции на всех платформах. Успех даёт код 0, четыре строки результата в stdout; таймаут ограничивает сетевые операции, а не полное время загрузки.

Среднее время равно сумме времён / 10. Скорость Mbps равна общему количеству байтов × 8 / сумме времён / 1 000 000. Деление на ноль должно завершаться понятной ошибкой, а не traceback. Пустой ответ допустим и даёт нулевой объём и скорость при положительном времени.

Этап проверяется командой `python3 download_speed.py --help` и локальными тестами следующего этапа. Команда должна показывать URL, таймаут и справочные параметры без сторонних библиотек.

### Этап 2. Проверки поведения

Создать `tests/test_download_speed.py` на pytest: обычные тестовые функции и assert, фикстуры с гарантированным освобождением ресурсов, `monkeypatch` для подмен и `capsys` для проверки вывода. Использовать фикстуру `httpserver` из dev-зависимости pytest-httpserver, которая управляет локальным сервером. Журнал обращений подтверждает ровно десять загрузок. Собственный сервер и счётчик активных обработчиков не нужны: счётчик мог ошибочно принимать завершение обработчика за ещё продолжающуюся загрузку. Последовательность обеспечивается обычным синхронным циклом в `measure` и проверяется при чтении кода. Проверять полное чтение тела, подсчёт байтов с Content-Length и без него, пустые тела и перенаправления. Для перенаправлений десять означает десять логических загрузок; дополнительные HTTP-обращения внутри перенаправлений учитываются во времени.

Проверить HTTP 404, таймаут сервера, неверную схему и недопустимые таймауты. Для CLI проверить код выхода, наличие понятного stderr и отсутствие успешной сводки после ошибки. Проверить формулы на известных байтах и длительностях, подменяя часы при необходимости: тесты не должны сравнивать реальную скорость с фиксированным значением. Обработку Ctrl+C проверить через контролируемый KeyboardInterrupt без реальных сигналов процесса. На POSIX проверить SIGTERM в отдельном процессе CLI: дождаться начала медленной загрузки на локальном сервере, отправить `terminate()` и убедиться в коде 143, сообщении в stderr и отсутствии traceback и итоговой скорости. Использовать ограниченное ожидание и обязательную очистку дочернего процесса; тест SIGTERM пропускать на Windows, где `terminate()` принудительно завершает процесс и не проверяет Python-обработчик. Проверки привязаны к пользовательскому контракту, а не к внутренним вызовам функций. Для таймаута и SIGTERM использовать короткий потоковый ответ Werkzeug Response с событиями начала, освобождения и окончания; отдельная фикстура освобождает ответ после теста. Тест намеренно оборванного тела исключён: Werkzeug управляет формированием ответа; собственный некорректный HTTP-сервер ради одного сценария не добавлять. Защита от неполного тела в программе сохранена.

Запуск после `uv sync --locked`: `uv run --locked pytest -q`. Все тесты должны пройти без внешнего интернета. Серверы, соединения и потоки закрываются после каждого сценария.

## Приёмка

Прямой запуск и установленная команда показывают одинаковые поля и корректно выполняют десять последовательных загрузок. Для файла 1 MiB общий объём равен 10 MiB. Вывод имеет следующую форму; значения времени и скорости здесь иллюстративны:

    Requests:              10/10
    Total downloaded:      10.00 MiB (10485760 bytes)
    Average request time:  0.100 s
    Download speed:        83.89 Mbps

Несуществующий путь локального сервера даёт ненулевой код, понятную ошибку без traceback и без итоговой скорости. Неверный URL и таймаут отвергаются до сетевого обращения. На POSIX SIGTERM во время загрузки завершает CLI с кодом 143 без traceback и успешной сводки; Ctrl+C — с кодом 130. Локальные тесты проходят; версия установленной команды — 0.1.0. Отдельно зафиксировать, на каких версиях Python проверки действительно выполнены.

## Интерфейсы и зависимости

В `download_speed.py` определить `Measurement` как dataclass с `total_bytes: int` и `durations: tuple[float, ...]`; производные величины вычислять из этих данных. `measure(url: str, timeout: float) -> Measurement` выполняет десять загрузок. `main(argv: list[str] | None = None) -> int` разбирает параметры, выводит результат и возвращает код выхода. Прямой запуск использует `raise SystemExit(main())`. Детали вспомогательных функций исполнитель выбирает по необходимости.

Стандартные библиотеки обеспечивают всю работу программы; pytest и pytest-httpserver — dev-зависимости для запуска тестов, uv управляет окружением разработки и lock-файлом. setuptools — зависимость сборки, pipx — внешний способ установки, а не зависимость программы.
